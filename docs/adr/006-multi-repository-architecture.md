# ADR-006: Multi-Repository Architecture

## Status

Accepted

## Context

FSAMP is split into infrastructure, two services, a shared event contract, and
reusable CI/CD workflows. The repositories use different stacks and release
cadences, so one repository per responsibility keeps ownership and thesis
chapters clear.

## Decision

Use five repositories:

| Repository | Responsibility | Main Artifact |
|---|---|---|
| `fsamp-infra` | Terraform, AWS deployment, local AWS emulation, e2e/load tests, compliance docs | Terraform state and deployment workflows |
| `fsamp-gateway` | Java/Spring Boot ingress service | ECS container image |
| `fsamp-processor` | Python event processor and outbox publisher | Lambda container image, optional ECS image |
| `fsamp-event-schema` | Canonical JSON Schema event contract | Versioned schema artifact |
| `fsamp-code-ci` | Reusable GitHub Actions workflows and composite actions | Workflow templates |

Repository layout:

```text
fsamp-infra/
  terraform/
  docs/
  e2e/
fsamp-gateway/
  src/
  Dockerfile
fsamp-processor/
  src/
  Dockerfile
  Dockerfile.lambda
fsamp-event-schema/
  event.schema.json
fsamp-code-ci/
  .github/workflows/
  .github/actions/
```

## Deployment Coordination

Service repositories build and test independently. After a successful merge to
`main`, the service workflow dispatches a `deploy-dev` event to `fsamp-infra`.
The infra workflow resolves refs, builds immutable ECR images when needed, runs
Terraform, and records the deployed image tag in SSM Parameter Store.

Promotion is centralized in `fsamp-infra`:

```text
dev -> staging -> prod
```

`dev` deploys automatically. `staging` and `prod` use GitHub Environment
approvals, and `prod` depends on a successful `staging` deployment. Rollback uses
the previous recorded image tag or an explicitly provided immutable tag.

## Versioning

The event schema is versioned explicitly because both services depend on it. App
image tags are immutable deployment tags generated by CI/CD, with optional release
tags for human-friendly promotion.

`fsamp-infra/compatibility.yml` records the currently tested combination of
gateway, processor, schema, infrastructure, and shared CI versions.

The `current.event-schema` entry is the latest tested tagged repository release
and is updated by `update-compatibility.yml`. `current.event-contract` is the
independent wire `schemaVersion`; it has no tag of its own and is intentionally
excluded from release dispatches. A wire-version change must update the
canonical schema, producers, consumers, this entry, and the cross-repository E2E
expectation in one coordinated change. CI verifies that a package-only patch
release (for example `1.2.1` carrying contract `1.2.0`) remains compatible while
minor or major drift fails closed.

## Consequences

Positive outcomes:

- Clear responsibility boundaries
- Separate Java, Python, Terraform, and CI/CD toolchains
- Centralized environment promotion and rollback
- Easier thesis mapping from architecture to implementation

Trade-offs:

- Cross-repo changes need coordination
- E2E tests must assemble artifacts from multiple repositories
- Compatibility must be tracked deliberately

Mitigations:

- Keep the event schema as the contract source of truth
- Run cross-repo e2e tests from `fsamp-infra`
- Keep deployment orchestration in one workflow family
- Use Dependabot and compatibility updates for routine drift
